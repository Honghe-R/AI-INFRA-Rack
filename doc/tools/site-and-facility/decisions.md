# Site and Facility Editor Decisions and Open Questions

This document records decisions that the rest of the specification bundle depends on, and the questions still requiring owner sign-off. The decision register is normative: when two tool documents conflict, this register and the canonical enumerations in [Interchange Contract](interchange-contract.md) win, and the conflicting document must be corrected.

## Decision Register

| ID | Decision | Rationale | Affects |
| --- | --- | --- | --- |
| D1 | A `DRAFT` revision is **mutable in place** under optimistic concurrency (`If-Match` ETag). Commands version individual entities and write the change to the current draft; they do not create a child revision per edit. | Matches the single-draft, dirty-state work surface in [UI Pattern](ui-pattern.md) and the ETag rule in [Storage Shape](storage-shape.md). Per-edit child revisions would produce unbounded revision chains and break "current draft" identity. Branching is an explicit `base_revision_id` operation, not a side effect of editing. | All documents |
| D2 | `base_revision_id` identifies the revision a draft was branched from. `If-Match` identifies the exact draft state being edited. Both are validated; a matching ETag never excuses a stale or unrelated base revision. | Removes the "either/or" concurrency ambiguity in [Backend API Contracts](backend-api-contracts.md). | API, storage, UI |
| D3 | `FacilityEnvelope` is a **separate versioned protobuf sub-contract** referenced by the platform `DesignBlueprint`; it is not inlined into it. The blueprint carries `facility_envelope_ref { envelope_id, revision_id, content_checksum, proto_package }`. | Preserves the platform rule that authoring-to-verification uses versioned protobuf, without forcing one release cadence on facility and network schemas. | Interchange Contract, blueprint |
| D4 | Facility UUIDs are mapped to blueprint `uint32` design IDs by the verifier's **inverse index registry** at runtime compilation. The mapping is published with the runtime image; authoring never exposes `uint32` IDs. | Resolves the UUID-versus-`uint32` ID conflict without weakening stable identity in the authoring model. | Interchange Contract, Entity Model, blueprint |
| D5 | `available_capacity = firm_capacity * (1 - derating_factor) - reserved - accepted_allocations`, where `firm_capacity` sums only `FIRM` and `COMMISSIONED` capacity. `CONTRACTUAL`, `PLANNED`, `ASSUMED`, and `MEASURED` capacity states never contribute to firm availability. | Makes the formula in [Interchange Contract](interchange-contract.md) computable and consistent with the capacity checks in [Verification Requirements](verification-requirements.md). | Interchange Contract, Entity Model, verification |
| D6 | Allocation contention is resolved deterministically: `RESERVED`, then `CRITICAL`, then `HIGH`, then `NORMAL`, then `LOW`, then earliest `required_from`, then earliest request. Ties are an explicit rejection, never an arbitrary pick. | A reproducible allocator is required for audit and for the batch verifier to agree with the editor. | Interchange Contract, verification |
| D7 | A resilience requirement is expressed as an availability policy reference (`N`, `N+1`, `2N`, `2N+1`, `N+2`) plus fuel/water autonomy duration. On-site power equipment (UPS, generators, switchgear) remains owned by the Power Supplier Editor; this tool owns only the planning-level requirement, fuel/water storage capacity, and failure-domain declarations. | Resolves the duplicate UPS/generator ownership between this tool and Power Supplier in the [platform blueprint](../../architecture/ai_infrastructure_planner_blueprint.md). | Overview, Interchange Contract, Entity Model, blueprint |
| D8 | This tool owns parcels, buildings, floors, halls, support spaces, equipment yards, reserved areas, utility entry points, site routes, and site constraints. The Floorplan Editor owns rooms, zones, rows, racks, containment, and in-building pathways; Route and Pathway owns cable trays, conduits, and detailed pathway geometry. | Replaces the ambiguous `ROUTE`/room/hall overlap with an explicit boundary. Site `ROUTE` geometry is limited to site access and utility corridors. | Overview, Entity Model, UI Pattern |
| D9 | All authoritative geometry carries a project CRS in EPSG form plus an optional compound vertical CRS. WGS 84 GeoJSON is mandatory as the interoperable representation; the projected representation is authoritative for measurement. Default length tolerance is 0.01 m, default area tolerance is 0.01 m², and default residual tolerance for fitted transforms is 0.05 m unless a project policy overrides it. | Gives geometry validation, spatial indexing, and import review concrete rules. | Interchange Contract, Entity Model, storage, import |
| D10 | Normalized units are SI base/derived units: W, K, m, m², m³, s, and count. MW, kW, kWh, and similar display units are presentation-only. Network-entry capacity uses the `NETWORK_ENTRY_COUNT` basis, never a power unit. | Removes mixed-unit comparisons and makes `basis` meaningful. | Interchange Contract, UI Pattern |
| D11 | Capability coverage is **derived from validation**, not typed by a user. `NOT_PROVIDED` means no evidence exists; `PROVISIONAL` means evidence exists but is unreviewed, assumed, or warning-gated; `VALIDATED` means every applicable check for that capability passed with no error. A user may request provisional coverage but cannot assert `VALIDATED`. | Removes the duplicate source of truth between coverage records and the validation summary. | Interchange Contract, verification |
| D12 | Waivers, assumptions, and documents are first-class entities with their own shapes and tables, referenced by diagnostics and inspector tabs. A waiver never mutates a diagnostic or envelope; it suppresses the gating effect of a specific diagnostic for a named revision and scope. | The UI and governance rules reference these records but the shapes were missing. | Entity Model, storage, verification |
| D13 | The original `backend/` and `frontend/` code was **prototype scaffolding**, never a contract implementation: it used rectangle coordinates, in-memory state, and non-canonical entity names. **It has been removed.** The platform surface is now `apps/api` and `apps/web`, and the specification bundle remains the source of truth for both. | Kept so that a reader of an earlier revision does not mistake the removed prototype's decisions (x/y/width/height geometry, `SITE`/`CONSTRAINT` type names) for the contract, and so the reason the prototype was disposable is on record. | All documents |
| D14 | The tool declares a versioned assistant surface, capability set, UI-action types, and attachment policy, consistent with the [workspace assistant contract](../../workspace/ui-pattern.md) and the [chatbox LLM blueprint](../../workspace/chatbox-llm-architecture-blueprint.md). | The shell requires every tool to declare these, and the bundle previously did not. | Assistant, UI Pattern |
| D15 | The transactional metadata and geometry store is a **relational database with ACID transactions and a native spatial extension** (reference implementation: PostgreSQL 16 with PostGIS). Metadata, geometry, budget, diagnostic, and outbox writes for one command commit in a single SQL transaction. Cross-entity referential integrity is enforced by foreign keys where the schema declares a reference, by unique and check constraints, by write-time reference validation inside that transaction for references a foreign key cannot express, and by a scheduled integrity check. Tenant and project isolation uses row-level security. | **Revised** from the earlier document-store choice. A relational store gives the command change-set native ACID transactions and a co-located spatial index through PostGIS, and adds declarative foreign keys, check constraints, and row-level security that the document model had to reimplement in application code. Geometry remains locally queryable, so containment, intersection, and distance checks stay synchronous. | Storage Shape, Entity Model, verification, non-functional requirements |
| D16 | The canvas basemap is served by a **server-side tile proxy**, never browser-to-tile-server. The proxy holds provider credentials, meters tile requests by organization, project, user, and provider, enforces quotas and rate limits, honors each provider's cache and attribution policy, and never sends a provider key to the client. Google tiles are consumed through the licensed Google Map Tiles API under a billing account; OpenStreetMap data is consumed through a commercial tile provider or a self-hosted tile server; the public `tile.openstreetmap.org` endpoint is **not** used in production and is registered only under the obligations recorded in [D26](#decision-register). Required attribution is always rendered on the canvas, and a plan-only grid remains available when no provider is licensed or reachable. | Centralizes usage tracking and quota management, which browser-direct tile loading cannot provide, and keeps provider credentials and licensing obligations enforceable in one place. | UI Pattern, Backend API Contracts, Storage Shape, non-functional requirements |
| D17 | **`PUBLISHED` is a third lifecycle state.** Lifecycle is `DRAFT` (editable), `VALIDATED` (immutable, no applicable `ERROR` diagnostic), or `PUBLISHED` (immutable, published). Publication is a one-way `VALIDATED` to `PUBLISHED` transition; a correction or extension is a new `DRAFT` branched from the published revision. `published_at` remains as the transition timestamp. Rejection or revocation of an approval attestation does not change lifecycle state. | Publication is a permanent, externally consumed milestone that downstream tools gate on, so it must be a queryable state rather than something inferred from a nullable timestamp. | Interchange Contract, Entity Model, verification, API, UI Pattern, workspace shell |
| D18 | Cost, schedule, and sustainability data is **reference-only** in this tool. The Cost, Schedule, and Sustainability workspace owns the values; the facility envelope carries optional `CostScheduleReference` entries, and no facility command creates, edits, or deletes a cost, schedule, or sustainability value. References are traceability metadata and can never relax a geometry, capacity, resilience, or environmental check. | Keeps one authoritative owner for financial and sustainability data and prevents facility validation from depending on values this tool does not control. | Overview, Interchange Contract, Entity Model, API, non-functional requirements |
| D19 | BIM/IFC import is **in scope for the first release**, and the adapter layer is an **extensible, workspace-level framework**. IFC 2X3, IFC 4, and IFC 4X3 are supported in R1 through a registered IFC adapter. Adapters, extraction, converters, units and CRS resolution, artifacts, limits, and framework diagnostics are owned once at the workspace level; each tool owns only the mapping of extracted content to its own entities. Adapters are independently versioned, registered plugins described by `ImportAdapterDescriptor`; adding, upgrading, or retiring one MUST NOT require a change to the core pipeline, storage, API, or any consuming tool. Every adapter ships conformance fixtures for each supported version and a negative fixture for every declared limit and diagnostic. | The tool must ingest BIM models, and import is needed by several tools. A shared adapter framework isolates each format's parser, licensing, and fidelity limits from every tool's contract, so new formats and versions do not force per-tool or core changes. | Workspace import framework, Import Mapping, Interchange Contract, Overview, non-functional requirements, assistant |
| D20 | Imported files are **first-class project assets**, not tool documents. Every import entry point (project workspace, Assets surface, any editor, drag-and-drop, assistant promotion, or API) creates a project-scoped `ProjectAsset` with immutable versions, checksums, scan state, access classification, retention, and provenance. Tools **consume** assets by pinning an exact asset version and representation in an `AssetBinding`; a tool never owns, copies, or re-uploads the file, and a later asset version never changes an existing binding. | Import happens in many places and the same file is routinely useful to several tools. One project-level asset model gives a single provenance, access, retention, deduplication, and versioning story instead of per-tool copies that drift apart. | Project Assets, workspace shell, Import and Conversion Framework, Interchange Contract, Entity Model, API, storage |
| D21 | Retention is an approved **numerical policy per artifact class**, recorded in the retention table of [Non-Functional Requirements](non-functional-requirements.md) for tool-owned classes, and in [Workspace Retention](../../workspace/retention.md) for workspace-owned classes. Idempotency records are retained **7 days**, job records **90 days**, and signed URL grants are **not persisted** (URL lifetime only). Backup retention is 35 days; restore-test records 24 months; import reports and validation runs life of the referencing revision plus 24 months; Facility Envelope protobufs project lifetime plus 7 years; exports 90 days; audit records 7 years. Workspace-owned classes — project assets and versions, asset representations, previews and tiles, and the proxied basemap tile cache — are defined in [Workspace Retention](../../workspace/retention.md) and are not restated here. A legal or regulatory hold overrides every value, and a retention value is changed only by a versioned configuration change with an audit record. | Q4 was the last open question, and every other artifact class and deletion rule depended on it. Fixing per-class durations makes the retention table, the object-lock period for published envelopes, and the deletion rules computable and auditable, and retires the interim defaults. Seven days for idempotency records exceeds any realistic client retry window while keeping the record store bounded; ninety days for job records covers an import or validation investigation cycle. | Non-Functional Requirements, Workspace Retention, Backend API Contracts, Storage Shape, verification |
| D22 | The store applies a **tenant-key discipline**: `project_id` is part of every primary key, every unique constraint, and every foreign key, so a stored reference cannot cross projects. The append-only classes `outbox_events` and `import_features` are **range-partitioned by time**, so retention expiry ([D21](#decision-register)) is a partition detach or drop rather than a mass delete. `facility_diagnostics` cannot be time-partitioned: its self-referencing `supersedes_diagnostic_id` foreign key would need the partition key in the referenced key, while the superseding row carries a different timestamp. It stays an unpartitioned append-only table with the full tenant-key treatment. The mutable graph tables stay unpartitioned in the first release, but their identities already include `project_id`. The horizontal target is **hash partitioning by `project_id` or Citus-style sharding with `project_id` as the distribution column**; list-partitioning one partition per project is rejected. | PostgreSQL requires the partition key in every primary key and unique constraint, and a foreign key that references a partitioned table must carry the partition key too, so this discipline is a prerequisite for any partitioning or sharding. Paying it once, up front, turns a later move to hash partitioning or sharding into a metadata operation instead of a data remodel. Composite tenant keys additionally enforce cross-project reference integrity in the database, which row-level security alone does not. Time partitioning on the append-only classes makes retention a structural operation. List-per-project is rejected because one deployment holds thousands of projects, where per-project partitions would bloat the catalog and the planner. | Storage Shape, Entity Model, Non-Functional Requirements, storage |
| D23 | Project asset **uploads are API-mediated**: the client streams bytes to the asset version's content resource, and the service writes them to object storage, computes the `content_checksum` itself, and enforces the declared size and media type while the stream is in flight. **Downloads keep signed URLs** — content is immutable, reads are cacheable, and a read grant carries no write capability. Bytes are deduplicated by `content_checksum` after intake, and a checksum supplied by the client is a hint about an already-held version, never evidence of content identity. Resumable and chunked uploads are **not specified in this revision**: the signed-URL design carried multipart resumability for free, so large-file intake must design a session resource and its completion call before rollout. | No write capability leaves the service, so there is no upload URL to leak, scope, or replay, and the bucket needs no write path reachable from the public internet. The authoritative checksum is observed by the service rather than reported by the client, which removes both the trust question and the cost of hashing multi-gigabyte files in a browser. One intake path means authorization, idempotency, size and media-type policy, and rate limiting are applied before a single byte is stored. It composes with limits the platform already specifies — a 256 MiB geometry command body — instead of introducing a second trust boundary at the object store. The accepted cost is that the API becomes a data path: intake consumes API bandwidth and a connection per in-flight upload, egress is paid twice (client to service to store), and uploads must be sized against load-balancer and CDN request timeouts. | Project Assets, Storage Shape, Non-Functional Requirements, Backend API Contracts, Import and Conversion Framework, workspace shell, deployment |
| D24 | **Asset versions are per-asset; the stored object is project-level.** `asset_versions` is unique on `(asset_id, content_checksum)`, so one asset never holds the same bytes twice, and identical bytes across different assets share a single stored object through a project-level content index. A repeat upload to the same asset returns that asset's existing version; a repeat upload to a different asset creates that asset's own version row and reuses the object. Provenance and version history stay per asset. | The project-wide uniqueness stated in the first draft of [Project Assets](../../workspace/project-assets.md) was unsatisfiable with per-asset version ownership: a second asset with identical bytes would have had to adopt another asset's version row and would then list no versions of its own. Keeping versions per-asset and sharing only the object satisfies deduplication and per-asset provenance at once. | Project Assets, Storage Shape, Entity Model |
| D25 | A representation is unique per `(asset_version_id, kind, producer_id, producer_version)`. Re-running the same producer version replaces that record's content in place, and a **new producer version** creates a new record while the previous producer version's record is kept and marked `STALE`. | The asset schema makes that tuple unique, so "a forced re-run creates a new representation and marks the previous one STALE" in the first draft of [Import and Conversion Framework](../../workspace/import-adapters.md) was unsatisfiable for the same producer version. Making a producer-version bump the supersession event keeps one live record per producer version, which is exactly what idempotent re-processing needs. | Import and Conversion Framework, Project Assets, Data Shapes |
| D26 | The public OpenStreetMap tile server **may be registered as a provider** (`osm-public`), exercised through the same server-side proxy as every other provider, subject to the [Tile Usage Policy](https://operations.osmfoundation.org/policies/tiles/): a `User-Agent` that names the deployment, an accurate `Referer` where one is configured, a cache honouring server headers with a **minimum seven-day** TTL, viewport-only fetching with no prefetch, bulk, or offline mode, visible `© OpenStreetMap contributors` attribution, and no availability guarantee — the policy states that commercial access may be withdrawn without notice. The identity headers are configuration (`MAP_OSM_USER_AGENT`, `MAP_OSM_REFERER`), held on a non-secret `requestHeaders` descriptor field that never reaches a client, and the provider carries no quota relief: it is metered like any other. | Owner decision (previously D16 forbade the public endpoint outright). A no-credential basemap makes the canvas usable out of the box and in development. The obligations are enforced in configuration and documented rather than assumed, and the SLA-backed `osm-commercial` provider remains the production alternative. | D16, W5, UI Pattern, Non-Functional Requirements |
