# 2026-09-22 — The assistant stops saying things that are not true

A work record, not a specification. The day began with a pasted failing transcript and one
instruction — *move the Central Chiller Plant into the Generator and Chiller Yard* — and the
assistant answered that it had, repeatedly, while the revision, the canvas and the chatbox each
disagreed in a different way. Six threads came out of chasing that: the write, the confirmation,
the canvas, the record, the wire format, and the usage popover. Every fix is in `8e1972e`.

## What landed

### The write: an identifier the model cannot copy

Three separate refusals, all of them asking the model to reproduce something only the server
knows.

* **`get_entity` "is missing …"** and invented uuid tails. A model cannot copy a `gen_random_uuid()`
  from a tool result into an argument without garbling it, and the surface was asking it to. Entity
  references now accept **display names** as well as uuids, resolved through a targeted
  `list_entities` read: a name that resolves to nothing is a `404 ENTITY_REFERENCE_NOT_FOUND`, and
  one that resolves to two things is a `422 ENTITY_REFERENCE_AMBIGUOUS`. Silently returning an empty
  result for an id that named nothing was the original defect — "the yard's BOUNDARY query returns
  zero geometry records" was a wrong id, not an empty yard.
* **Utility reads returned no names.** `list_utility_sources` and `list_utility_interfaces` now carry
  the registered `displayName`, and an interface nests its `source` as its own object. Four sources
  distinguishable only by an opaque id is how "Central Chiller Plant" became unnameable to the
  resolver.
* **`set_geometry` "is missing `base_revision_id`"** — the last two uuids the model was asked for.
  Both preconditions are now bound by the projection from the resolved context. They are bound on
  the capability's own arguments and never on the composed `apply_change_set`, which takes `etag`
  rather than `if_match`: binding them a second time injected a field the command does not declare
  and refused every write.

### The confirmation: execute what was shown

The gate was right and the client was unreachable — the transcript rendered "needs confirmation"
with nothing to click. Worse, once a decision was sent the model was asked to re-propose the call,
and a live turn answered *"I ran the write. Here's the result…"* with **zero tool calls** while the
draft ETag never moved. Confirming now hands back the recorded `{ callId, name, arguments }` and the
server runs exactly that, then asks the model only to report the result. The confirmation card shows
the tool and the redacted arguments, and a gated turn that is not persisted no longer pretends to be
part of the conversation.

### The canvas: a change the surfaces could not see

The write committed inside the turn, server-side, while the canvas held the envelope it had read at
turn start. So a confirmed move landed in the database and stayed invisible in the one place it was
asked for — "the assistant says it moved it" until the page was reloaded. A turn now records
`wrote` per successful call from the capability's own access mode, derives `draftChanged` from the
rounds, and the client dispatches `reloadEnvelope` through the effects channel, which asks the
mounted canvas for its own `useFacilityEnvelope().reload()`. The flag is derived from the same
record the transcript discloses, so the two cannot disagree.

### The record: what the model was after, not only what it called

The timeline showed rounds, tool names and durations. None of that says what the model was *trying*
to do. The record now carries, per round, the model's own words — the reply envelope's payload, and
the provider's separate thinking channel — bounded at fifty thousand characters, entity-linked
exactly as the reply is.

The discovery that made this worth doing: **for this deployment the model narrates in
`reasoning_content`, not in `content`.** Everything it reasoned was computed for an audit line and
thrown away; nothing had ever read it.

Also in the record: what the turn cost (input, output, cached), which request it was, and the
server's own notices, which reached the client only to be dropped. A call that changed the draft is
named rather than left as a duration. A live turn is marked `live`. And the reader can now close it:
a click on the summary settles the disclosure for the rest of the turn, where an unconditional
auto-open re-opened it under a reader who had just closed it — rounds land every few seconds, so the
head was effectively dead for exactly the turn you most want out of the way.

### The wire: a notice that was our fault

`Unknown UI action "highlight_entity@1@undefined"` was the first visible symptom, and the model was
not at fault. The prompt listed the actions as `highlight_entity@1`, so the model copied that token
whole into `type` — a well-formed action in a spelling the registry refused. Four layers came out of
following it:

1. **We invited it.** The prompt now names each action with the version as its own field and states
   the payload fields: `highlight_entity (version 1) — payload { entity_id: uuid (required), … }`.
   It had been naming the actions and saying nothing about their arguments, so the model invented
   them: `{ name: "Central Chiller Plant" }`, then `{ entityName: … }`, then the same fields beside
   `type`. Three correct intents, three unreadable shapes.
2. **We refused the punctuation, not the intent.** The registry reads `type@version` too.
3. **We lost requests in silence.** A reply whose payload carried a raw newline is invalid JSON, and
   discarding the envelope discarded its `uiActions` with it — no notice anywhere. The server now
   repairs control characters inside string literals, the same recovery the browser already did for
   display.
4. **The model prints the request instead of mailing it.** Even with the shape written out, it
   answered in prose and then printed the envelope — or the action object alone, with `entity_id`,
   `entity_type` and `label` correct to the letter — in a fenced block. Both spellings are now read.

And then the last piece, which is the one the chatbox was showing: **what was consumed is taken back
out of the reply.** An instruction is not an answer, and leaving it in the bubble is how a chatbox
comes to display its own wire format underneath a sentence that already said the plant was
highlighted. Only what was consumed is removed — JSON the model wrote for a person stays, because
this is not the layer that decides an answer may not contain braces. A turn whose whole reply *was*
the request has no words of its own, so the answer position states the action's own registry
description rather than leaving a blank bubble under a canvas that visibly changed.

### The usage popover: two columns

Two scopes side by side rather than stacked, because the only question asked of those numbers is a
comparison — how much of the month's allowance this conversation accounts for. Cached tokens ride in
both columns **beside** the totals, never inside them: a cached prompt is the same tokens at a
fraction of the rate, so "how much was already warm" and "how much did this cost" are different
questions. The `userSummary` query gained the cached sums; the columns are held by
`repeat(auto-fit, minmax(150px, 1fr))` — driven by the panel, not the viewport — with tabular figures
so the two sides line up digit for digit.

## What I could not reproduce

The reported reset — *"after confirming, old turns are lost; the timeline restarts from turn 1"* —
**does not reproduce**, and I want that on the record rather than a fix for a bug I never saw.

Two live runs through the real model, gating a read and then a write, preserved everything: 16 → 18
and 18 → 20 turns, the session id unchanged, the write applied. The transcript-restoring logic was
already covered by a seven-exchange test that confirms in place.

What looked like the culprit was a new session row (`f67fffab`) timestamped 33 seconds after the
17-turn session's last turn. The database said otherwise: gated turns are **not persisted**, so the
row is created when a request *starts*, and that turn was a plain re-read. The user had clicked New
session, on my advice, one message earlier. I had been reading a session's creation time as if it
were the time of its first stored turn.

Two latent paths that *can* produce the symptom were closed anyway, because they are the only ones
left: `restore()` replaced `state.turns` unconditionally, so a history read that finished after the
reader sent their first message swallowed the live conversation; and a remembered session whose read
came back empty sent the client looking for another — plausibly one-turn — session to stand in for
it. A rehydration now only fills in, and defers to a conversation already on screen.

## Decisions worth keeping

* **Never ask a model to reproduce an identifier it cannot copy.** Every `gen_random_uuid()` in an
  argument is a defect waiting for a long conversation. The server binds what it knows; the model
  names what it can see.

* **A confirmation confirms the arguments the user saw.** Re-proposing the call to the model is what
  let a turn narrate a write that never happened. The recorded call is executed; the model only
  reports.

* **Derive the flag from the record, don't track it beside it.** `draftChanged` is computed from the
  rounds, so the envelope, the disclosure and the canvas cannot drift.

* **A disclosure belongs to the reader.** A click on the summary is the reader's own activation; the
  `open` prop moves the element without one. Nothing else may count as a decision.

* **Read the spelling, refuse the intent only when it is wrong.** `type@version`, a printed action, a
  payload with a literal newline: each was a correct request in a shape we did not expect, and each
  was being lost silently. The audit for "what did the model actually write" was reading the stored
  turn out of the object store — not inferring it from the notice.

* **Remove only what was consumed.** Everything else a model writes is content.

* **Cached tokens sit beside the totals.** Folding them in would make the total say something it does
  not.

* **Narration is a guard, not a reading limit.** The first bound was two thousand characters, and a
  live turn reported "narration truncated" on the reasoning the reader had asked for. The thinking
  *is* the thing being read.

## Defects

**Three I introduced.**

* **The prompt that invited the malformed identity.** Naming the actions `type@version` produced
  `highlight_entity@1@undefined`, and I then wrote a `describeAction` helper to stop `undefined`
  being printed — treating the symptom. The model was right and the prompt was wrong.
* **A narration bound that cut the feature's own content.** Two thousand characters, chosen to
  protect a stored turn, against a reasoning trace that routinely runs longer.
* **A test expectation of 16 where the answer was 14.** Seven exchanges are fourteen turns, and the
  failing assertion was evidence that the earlier turns survive — which is exactly what the test
  existed to prove. It now asserts the invariant (the count is the same before and after confirming)
  rather than a number.

**Four the code was already carrying, all silent.**

* **An unparsable envelope discarded its UI actions** with no notice: a raw newline inside the
  payload makes the object invalid, and the reply was thrown away whole.
* **A rejected action and a dropped action looked identical from outside** — nothing in the
  transcript said either had happened.
* **`sessions.ensure` mints a new session when a supplied id carries a different `context_key`,**
  and says nothing. This is still open below: it is the one remaining route to "the timeline
  restarts from turn 1".
* **The API suite has five failing tests in `assets` and `imports`** (streaming, holds, signed URLs,
  RESTRICTED grants, import processing — all `404`s). They are untouched by this work and were
  failing before it; I have not diagnosed them.

## Verification

* **Live, against the real model** (`deepseek-flash` at `api.deepseek.com`), driven in headless
  Chrome over CDP with `scripts/ui-shot.mjs`:
  * Confirm a write: transcript `18 → 20` and `20 → 22` turns, session unchanged, and the facility
    envelope read count — counted from `performance.getEntriesByType('resource')` — went **1 → 2**.
    That count is the fix: the canvas re-read the revision because the turn said it had changed.
  * Collapse a live record: `open/rounds=1` → click → `closed/rounds=1` → **a new round arrived**
    (`rounds=2`) and it stayed closed → click again → open.
  * Narration: `narrated=2` at t+6s and t+12s while the turn was still running, and the same
    thinking text was intact after a page reload.
  * A highlight landing on the canvas: `highlighted=0` on two runs while the request was being
    dropped, `highlighted=1` once it was read.
  * Wire format in the transcript: **3 leaking turns → 0** across 58 restored turns, including the
    one pasted in the report.
  * Usage popover: two columns at `x=594` and `x=936`, both `y=792`; `THIS CHAT Input 64,808 Output
    556 Cached 62,336 Total 65,364` beside `OVERALL Input 2,213,261 Output 94,984 Cached 1,133,056
    Total 2,308,245`; at a 620px viewport still side by side at 260px each with **no value
    overflowing**.
* **Suites green**: facility **386**, assistant **67**, web **601**, plus the API's
  `assistant-projection` **2**. Over the stretch I ran them the assistant suite went 53 → 67 and web
  587 → 601; the new tests name the seams that had none — the confirmation keeping the conversation,
  the write marking and the envelope reload, the reader's collapse, the narration and its guard, the
  salvage and stripping of a printed request, the UI-action identity in both spellings, and cached
  tokens across both usage scopes.
* **The object store as evidence.** Reading the newest turns out of MinIO (`manifest.json.gz` plus
  each turn object) is what separated "the model said X" from "the prompt invited X", and it is how
  the model behaviours above were found rather than guessed.

## Open

* **`sessions.ensure` still starts a new conversation silently** when a supplied session id carries a
  different `context_key`. If that ever fires, the client adopts the new id and the timeline
  genuinely restarts at turn 1 with the old history orphaned. The fix is to make it visible rather
  than to change the behaviour — a revision switch does need a new conversation.

* **UI actions travel by a route this model writes unreliably.** Reading a printed request works, but
  the model uses the tool-call path perfectly and the envelope path inconsistently. Moving UI actions
  onto a tool call is the architecturally honest fix, and it is a contract change, not a display one.

* **The client-side stripping is broader than the server's.** It will also hide a fenced, valid
  action object that a model wrote *as an example*. The server only removes what it read; the client
  cannot tell "here is the request" from "here is what a request looks like", and I chose clean
  transcripts over that distinction. Worth revisiting if a model ever explains the actions.

* **Five pre-existing API test failures** in `assets` and `imports`, undiagnosed.

* **A turn's UI actions are not shown in the record.** With prose present, the reader cannot see
  which action a turn asked for — only the effect. The annotation only appears when there is no
  prose at all.

* **The narration guard is fifty thousand characters per round**, which a very long reasoning trace
  could still hit. Unbounded is defensible now that the thinking is the point.

* **Live data, for the record:** the draft is revision `59cb023e` in project `2f4549d0`, and Central
  Chiller Plant is **inside** the Generator and Chiller Yard, as last asked. Diagnosing this cost
  several ETag versions — the confirmed-write tests deliberately wrote the connection point's own
  coordinates, so the design did not change while the version counter did.
