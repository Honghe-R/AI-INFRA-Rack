# 2026-09-20 — A second tenant, a second campus, and the organisation that follows the identity

A work record, not a specification. Today's change is one thread: the development seed now
creates **two** organisations with a project each and the users that make each one worth
having, each project gets its **own** facility graph rather than a copy, and a session acting
as an identity in the second organisation lists the second organisation's projects.

## What landed

### Two tenants in the seed

`scripts/lib/dev-identities.mjs` gains `DEV_ORGANISATIONS`, and the identity list grows from
four to six. The seed creates both organisations, a project in each, each project's first
scenario and draft revision, and the role assignments that make every identity in the account
control a real user holding a real role.

| Organisation | Project | Identities |
| --- | --- | --- |
| Development organisation | Northern DC Campus | `dev-user`, `dev-editor`, `dev-viewer`, `dev-org-admin` |
| Cascade Cloud | Cascade Ridge Campus | `dev-second-admin`, `dev-second-viewer` |

`scripts/dev-seed-facility.mjs` seeds the facility graph and the five project assets into
**both** projects, so the second tenant is a demo rather than an empty row.

### Two campuses, as data

The seed's graph was inline constants for one site. It is now a **layout**
(`scripts/lib/dev-facility-layouts.mjs`): geography, projected CRS, containers, phases,
failure domains, utilities, reserves, constraints, assumptions, and the sample files are all
data, and `dev-seed-facility.mjs` is the plumbing that writes one into a revision.

The sample files are derived from the layout, so a tenant's site plan carries that tenant's
coordinates and names. Seeding one campus's plan into the other would be worse than seeding
none: it is a document a reviewer would trust.

### The organisation follows the identity

A session's organisation was a build-time fact (`VITE_ORGANISATION_ID`), which cannot express
"this identity is in another organisation". The dev server now declares `organisationId` on
the identities it knows, `resolveDevOrganisation` picks the one for the current subject, and
`PlatformApp` resolves before the first project read. Only the primary organisation falls
back to the env var, because its id is allocated by the seed on first run.

### The account menu says who, not what

The menu offered each identity's *role label* as the headline and the reason it exists as a
note ("Authors and validates; cannot publish, approve, or grant a waiver"), so it read as a
list of permission bundles rather than a list of people. Choosing between them meant comparing
descriptions of what each one may do — and it never said who you were acting as.

An identity is now a **person**, the **organisation** they belong to, and the **role** they
hold there. Each organisation holds **one identity of every role**, and the menu groups them,
because the organisation was the thing repeated down every row:

The names are fiction, and that is the point: a person's name is the one thing on the line
that cannot be mistaken for a permission. The `x-dev-subject` login stays visible beside it,
because that is what the proxy mints a token for and what an authentication error names — but
it is how the identity is *assumed*, not part of who it is. Every role now appears twice, once
per organisation, and the group is what tells the two apart — which is also the second tenant
made visible in the UI rather than only in the seed.

The list was also **unbalanced**: four identities in the first organisation, two in the second,
with the second organisation holding no editor and a second administrator that was really just
its owner. That is not a cosmetic difference. A role held in one tenant and not the other is a
question the second tenant cannot be asked, and the questions that were missing are exactly the
ones worth asking — whether an editor elsewhere may author, whether an organisation
administrator elsewhere is refused the project keys their counterpart is refused. The second
organisation now has an editor and a separate organisation administrator, and the two lists
mirror each other role for role. `system-admin` is deliberately not among them: it is a
system-scope role held across organisations and owned by none, so one of every organisation
role is four identities, not five.

The menu is a separate `AccountMenu` component, so what it says can be asserted by rendering
it — the menu itself only exists once opened, and the shell is tested with
`renderToStaticMarkup`. Those tests read the **real** list the dev server serves, projected
exactly as it serves it, so the balance between the two organisations is itself asserted
rather than described.

### The assistant's message area grows, up to a limit

The composer's textarea was one row tall with a fixed maximum, so a three-line message was read
through a slot the width of a line: the box never grew, it scrolled in place. The other extreme
is worse — a box tall enough for the longest message anyone writes covers the work surface the
assistant is being asked about — so the box now grows with what is typed into it and stops at a
limit, past which it scrolls.

The limit is not written down twice. `max-height` in the stylesheet is the cap, and the
component reads it back as a resolved pixel value, so `max-height: 9em` still scales with the
font size and there is no constant in the JavaScript to drift from it.

Three details are load-bearing rather than defensive:

* **The height is reset to `auto` before measuring.** A box already at its cap reports
  `scrollHeight` as that cap, so without the reset it could grow and never shrink.
* **The measurement is a layout effect, not an effect.** On an ordinary effect the keystroke
  that adds a line paints at the old height first, and the box visibly jumps.
* **A `ResizeObserver` re-measures on width changes.** A narrower composer wraps the same text
  onto more lines, and the window is not the only thing that changes the width — collapsing the
  sidebar does too. The observer reacts only when the element's own width changed, so the
  height it writes cannot retrigger it.

The manual resize handle went with it. With the height set from the content, a drag would be
undone by the next keystroke, and a control the user can move but which the component
immediately moves back is worse than no handle.

### The assistant's side of a turn

A failed turn was reported by marking the **user's** turn failed, so the error and the retry
were rendered inside the message the user had written. The screenshot that prompted this shows
what that costs: a bubble containing the question, then "No LLM provider is configured…" and a
Retry button, all as though the user had said them. The transcript is the only record of the
conversation, and a message that has been edited to contain the system's answer to it is not
the conversation.

The assistant's side of a turn now exists from the moment the message is sent. Sending appends
two turns: the user's, and an empty assistant turn with `STREAMING` status. The transcript
renders that as *Assistant is thinking…* in the assistant's own bubble, which is where the
answer will appear, and it is announced by the transcript's live region rather than by a second
indicator somewhere else in the composer. When the provider answers, the reply **replaces** the
placeholder — `replaceTurn` writes the placeholder's id onto the settled turn, so React updates
the row in place instead of unmounting one node and mounting another, and a screen reader hears
the new text rather than an insertion. When it fails, the same turn is marked `FAILED` and
carries the error, the correlation id, and the retry. The user's turn is never marked: what they
wrote is what they wrote.

Two consequences worth stating:

* **Retry is resolved against the transcript, not against the failed turn.** The retry control
  sits on the assistant's failed turn, which has no text, so `retry` walks up to the last user
  turn above it and re-sends that — and drops the failed turn, since the reply is being asked
  for again. It also takes the draft out of the field, which the failure had put back.
* **A stop is not the provider failing.** Aborting the fetch raises a `DOMException` whose
  message is "signal is aborted without reason"; that is what the browser did, not what
  happened to the reader, who pressed Stop. A cancelled turn now reports "Stopped before the
  assistant answered." with an `ASSISTANT_TURN_STOPPED` code of its own.

A turn with no text of its own renders no prose block and no copy control: there is nothing to
copy on a placeholder, and on a failure the text is the error rather than an answer.

### The transcript opens at its end, and the wait is legible

Two smaller things about the same surface.

**The conversation is read from its end**, so `AssistantTranscript` scrolls its list to the
bottom in a layout effect keyed on the turns. The composer unmounts that list when it
minimizes — the launcher stands in its place — so running on mount *is* "scroll to the bottom
when expanded", and the same call covers a turn arriving while the composer is already open.
A layout effect for the same reason the message area's height uses one: the position has to be
right before the paint, or the panel opens showing the top of the conversation and jumps.
`scrollHeight` rather than `scrollIntoView` on the last turn, because the list is the only thing
here that scrolls.

**The thinking line has a little motion**: the three dots after "Assistant is thinking" pulse in
sequence, one keyframe with staggered delays. The words carry the meaning and the dots carry the
motion, so the animated spans are `aria-hidden` — a screen reader reads the sentence once rather
than once per frame. The keyframe is the stylesheet's first, and it comes with the stylesheet's
first `prefers-reduced-motion` block: decoration that ignores a reduced-motion request is a
defect rather than a flourish, and a test asserts both halves.

**The wait survives the composer's own state.** Minimizing does not touch the session: the
controller lives in `useAssistantSession`, which `App` holds above the composer, and collapsing
only swaps the frame for the launcher. Verified rather than assumed, because the failure mode
would be a hook recreated under the composer — a conversation silently restarted by pressing
Minimize: with a turn in flight, minimizing, expanding again while it was still pending, and
minimizing once more, the transcript held `[user, Assistant is thinking...]` on the way back,
the launcher grew its unread dot 603 ms later when the reply landed while minimized, and
expanding showed `[user, ready]` at the bottom of the list.

### Finding a feature on the canvas

The canvas could be panned and zoomed and its shapes clicked, but there was no way to go the
other way — from a name to the thing it names. A planner reading a drawing knows the name
before the location, and the only route to a hall was to hunt for it by eye.

There is now a search control in the top-right corner: one icon until it is wanted, then a
field beside it with the results under both. Hovering or focusing a result highlights it on the
map; choosing one selects it, which is what clicking it on the canvas does. Focus does what
hover does, so the affordance is not pointer-only.

Three decisions are worth recording:

* **The search runs over what is drawn.** `searchShapes` is handed the projected overlay — the
  shapes whose layers are switched on — so a result is always something the map can highlight.
  The alternative reads better until the first hidden layer: a hit the canvas cannot show is a
  promise the tool cannot keep. A query that finds nothing while features are behind a hidden
  layer says so, from a count the shell already has, rather than reporting a plain no match.
* **The ranking grades the match before it grades the field.** A field that *is* the query
  beats one that starts with it, which beats one that contains it; only then does a name beat a
  type, which beats a role, which beats the layer name. So typing "hall" returns the feature
  called Hall before "Data Hall 01", where a pure field-weighting would have returned whichever
  was drawn first. Equal scores keep draw order, which is the order the map reads in.
* **The control is a disclosure, not a listbox.** There is no active descendant to manage and
  no value to commit, so each result is a button: Tab reaches it, Enter activates it, and the
  panel is announced by `aria-expanded` and `aria-controls`. Escape clears a query first and
  closes on the second press, returning focus to the button — the field is about to be
  unmounted, and focus in a removed element falls to the body, which loses a keyboard user's
  place. A press on the map closes it and leaves the focus alone, because that is the user
  choosing a new place.

The panel's open state and its query are uncontrolled, with `defaultOpen` and `defaultQuery`
for the tests: a static render would otherwise only ever show the icon, and every state worth
asserting — the empty panel, a result list, no match, the count of hidden matches — is behind a
click.

**The panel's own scroll, which the first version got wrong.** It was rendered inside the map
surface, and the surface is an element that disables the browser's touch gestures
(`touch-action: none`, or a finger drag scrolls the page instead of panning) and claims the
wheel to zoom. Both of those reach **every descendant**, so a wheel over the results zoomed the
map instead of scrolling them, and a finger could not scroll them at all — the pointer guard
that keeps the map out of a control's way stops the pan, but the browser still refuses to scroll
a box whose ancestor has disabled panning. Ten results is the point at which the list scrolls,
so this was reachable on the first real search.

The control is now a **sibling** of the surface, positioned against the canvas instead, which
puts the map's gesture handling outside the panel's ancestry rather than working around it. The
surface keeps `touch-action: none` for the map, and its overlay marker stays for the controls
that are still inside it.

The fix is verified with a **real** wheel rather than a dispatched `WheelEvent`, because a
synthetic event does not perform the browser's default scroll — and the default scroll is
exactly what was broken. `ui-shot.mjs` gained a `--real-wheel <selector>,<dx>,<dy>` flag for
it, dispatching through the input pipeline the way `--real-click` does, and the two halves are
measured against each other: a wheel over the panel leaves the zoom at 17 with the panel's
`scrollTop` going 0 → 143, while a wheel over the map moves the zoom 17 → 15 and leaves the
panel alone. Read from the running shell, the panel's ancestor chain contains no
`touch-action: none` element (the surface still has one), and the panel still overflows with
`overflow-y: auto`.

## Decisions worth keeping

* **Two organisations, not one with more roles.** A reference that crosses a tenant, or a
  permission resolved at the wrong one, is the class of defect row-level security and the
  tenant-key discipline exist to catch, and one organisation cannot exhibit it. No identity
  belongs to both, so crossing the boundary is refused rather than merely unusual.

* **The second organisation's id is a constant; the first organisation's is not.**
  `e3be6d4b-a1aa-5b44-bef0-dd8ff28a5e2d` is UUID v5 over the seed namespace and
  `dev-organisation:cascade-cloud`, fixed because a session has to know which organisation to
  list *before* it has read the database. The primary id was allocated before this list
  existed, and fixing it now would strand the project that already points at it — so the seed
  keeps allocating it and writes it to the env file, which is the one thing that knows it.

* **The two campuses differ, and differ in what they get wrong.** Identical demo data
  would make a leak across the boundary look like a correct answer. More importantly, a seed
  that always validated would exercise no finding: Northern DC is missing connection points
  and commissions cooling after the phase that consumes it (9 errors), while Cascade Ridge
  supplies every connection point, has precise phase dates and a water envelope (so those
  findings never fire), and instead claims N+2 against two and one independent paths
  (2 errors). The same validator, two different reports.

* **A requirement's own `availability_policy` is the claim; the pinned policy
  corroborates it.** `redundancy.path_count` originally read the required count from the
  referenced policy in preference to the field the requirement declares, which meant a
  revision claiming N+2 while pointing at an N+1 policy was silently measured against N+1.
  The declaration now wins, and the reference is consulted only when the declaration is not
  recognised. Cascade Ridge pins a matching `campus-n-plus-2@1`, which is also the honest
  modelling: a requirement that claims a policy should reference that policy.

* **An identity is a person, an organisation, and a role — and that is the whole of it.**
  Everything else a development identity can be described by (the scope its role is held at,
  the permission it exists to exercise, the project it happens to be a member of) is a fact
  about what the identity is *for*. Those facts belong in the seed, where they are still
  recorded, and not in a control that answers "who am I".

* **Every organisation holds every role.** A development list is a set of questions to ask of
  the app, and a role missing from a tenant is a question that cannot be asked there. It also
  makes the menu legible: two symmetric groups of four read as two organisations, where four
  and two read as the first organisation and an afterthought. The cost is two more users, and
  two more rows in a menu that was grouped precisely so that rows could be cheap.

* **The dev server serves a projection, not the seed's record.** `clientIdentity` narrows each
  identity to the person, the organisation, the role, the subject to mint for, and the
  organisation id the client needs to list projects at the right scope. The seed's own list
  keeps the role key, the scope, and the organisation-scope read role, none of which is a fact
  about a person. Had the endpoint kept serialising the whole record, a later change to the
  menu could have put them back on screen; now they are not there to render. The unused
  `authority` field was deleted for the same reason — a field nothing reads is one that shows
  up in a payload by accident.

* **The projects list is checked at organisation scope.** An identity that holds only a
  project role can read everything in the project and still not find it: the list refuses, the
  workspace never opens. That is why every project identity also carries an
  organisation-scoped read role, and it is now recorded in the seed as the reason rather than
  left as a mysterious second assignment.

## Defects

**One I introduced.** `dev-second-admin` was seeded with a project role only. The owner of an
organisation is normally made its administrator by `createOrganization`, but the second
organisation is inserted *by id*, which skips that — so the second administrator could not
list their own project. The seed now grants organisation administration to each
organisation's owner explicitly, whichever path created it.

**One the seed would have applied to nobody.** `createUser` is idempotent, and its
`ON CONFLICT` clause refreshed `email` but not `display_name`. Every machine that has been
seeded — this one included — already has the six subjects, so the names in the table above
would have reached no existing user: the insert path never runs again. The `ON CONFLICT` now
converges `display_name` with `COALESCE`, so a declared name replaces the old one and an
undeclared one is left alone rather than nulled, which is what the existing `email` line
already did for its own column. A test asserts both halves. Verified against the development
database: the six subjects now carry the names above rather than the role labels a previous
seed wrote.

**One I inherited, and only the full suite could show.** `packages/imports/src/tests/adapters-kml.test.js`
turned a fixture URL into a path with `URL.pathname`, which is percent-encoded. Every KML and
KMZ test failed with `ENOENT ... /AI%20Network%20Infra%20Simulator/packages/...` — this
checkout's directory has a space in its name, so the adapter was handed a literal `%20`. Ten
tests were failing on this machine and would pass on any machine without a space in the path,
which is exactly the kind of failure that gets read as "not mine". `fileURLToPath` fixes it and
the package is green at 76 tests. It is committed separately, because it is not part of this
change.

**One I inherited.** Earlier test runs (mine, on 2026-09-18, before the cleanup order was
fixed) left 23 organisations and 29 users in the development database — `Validation Org …`
and `Worker org` projects, some with a partial facility graph. They were removed with the
same reverse-dependency order the tests now use. The database holds exactly the two tenants.

**A naming slip.** `resolveProjectFor` declared `organisationId` and returned
`organizationId`; the file is otherwise American-spelled, so the local was renamed.

**One the suite could not see.** The diagnostic supersession key was built from the
diagnostic's entity references alone. `redundancy.path_count` reports one constraint against
one resilience requirement once per resource kind, so POWER and COOLING had the *same* key,
and persisting the second marked the first `SUPERSEDED`: two shortfalls were reported by the
engine and one reached the store. The key now includes the resource kind, it is stored as
`computed.evidence_key` so a later run can match it, the API strips it as plumbing, and the
run's "close what it cleared" pass reads the stored key rather than rebuilding one — that
second half was a defect in the same change, because a rebuilt key without the kind marks
every live finding as cleared. A regression test now asserts that one constraint against one
entity yields two live diagnostics.

The existing tests could not catch it: every negative fixture produces exactly one finding
per constraint, so nothing exercised two findings that share an entity. The lesson is the
same shape as the ones in the 2026-09-19 record — the check exercised the code path without
exercising the case.

**One that was never a code defect.** The assistant answered `503 SERVICE_UNAVAILABLE` — "No LLM
provider is configured" — because the local `.env` had no assistant section at all: it was
copied on 2026-09-17 before the assistant host landed the same evening, so `LLM_*` was never in
it, and the host had never been assembled in this environment (the `assistant_*` tables were
empty, and the 503 is the designed behaviour of an optional integration). Every value is
environment-only by design — the endpoint, the model, and the name of a secret the environment
also has to hold — so nothing in the repository could have recorded it, and `node --watch`
re-reads source but not `.env`. The configuration is local and untracked, so the fix is local
too; what is tracked is the README's troubleshooting row, because the failure names the missing
variables and the next person should not have to infer that the assistant is optional.

## Open

* **The layouts are still hand-written.** A third tenant means a third layout by hand. A
  generator parameterised by building count, phase count, and a policy would make new
  tenants cheap, but it would also make every campus look generated.
* **The second organisation's roles are only exercised by hand.** The menu's tests read the
  real list and assert its shape, but nothing walks that list against the database to assert
  what each role resolves to: the API tests build their own users, and the effective keys below
  were read through the running stack. A test that seeded the shared list and asserted the keys
  each role gains and lacks would make the symmetry enforceable rather than verified.
* **The account control is grouped by organisation, and eight entries now fit.** Grouping was
  the response to six flat entries; at eight it is what makes the list readable. If a third
  organisation arrives, the groups are already there, and the menu's own height — not its
  width — is what would need a scroll.
* **The Vite dev server resolves identities from the seed's list, not from the database.** A
  hand-created user is not selectable; that is deliberate, and it means the list is the
  contract between three consumers rather than a query.

# 2026-09-20 (second thread) — The assistant tool surface, and the three milestones it was waiting on

T8 was scheduled to be a projection of the facility tool surface: capability descriptors,
declaration, argument redaction, UI-action types. It depended on T5, which was not built —
and when the dependency was inspected, T3's apply half and T6's allocator were missing too.
The decision taken was to build all three rather than declare capabilities with no command
behind them, so the surface would be real. This is the record of that thread.

## What landed

**T6 — capacity allocation.** `packages/facility/src/capacity.js` holds the two rules the
schema had left to a caller. `availableCapacity` is [D5] in one place: `commissioned ×
(1 − derating) − reserved − accepted`, where only `ACCEPTED` allocations count.
`contentionOrder` is [D6]: priority, then earliest `required_from`, then earliest request,
with the tied group returned so the command **refuses** it instead of picking a winner.
`requestCapacityAllocation` records the demand request and answers with a `PROVISIONAL`
allocation or a `REJECTED` decision naming the reason (`no_budget`, `insufficient_capacity`,
`contention_tie`) and the shortfall; `decideAllocation` is the authorized
accept/reject/revoke/expire and refreshes the budget's stored `allocated_value`/
`available_value` in the same transaction. `get_capacity_budget` now recomputes availability
from the formula rather than reading the projection back, so a budget written with a value
of its own cannot make the read assert an availability no allocation supports. Two resilience
divergences the reconnaissance found were fixed in the same thread:
`redundancy.path_count` and the fuel/water autonomy checks now measure **failure-domain
independence** by disjoint ancestor sets, through a bounded exact maximum-independent-weight
search, so two sibling feeds under one parent are one path, not two.

**T3 — import mapping.** `import-mappings.js` holds the entity-type↔geometry-role table, the
selector/cardinality validation, and the create/update/review commands for transforms and
mappings; any content edit returns a mapping to `UNREVIEWED`. `import-apply.js` reads the
binding's `FEATURES` representation from object storage, matches features to reviewed mappings
with the W4 selector matcher, previews the merge without writing, and applies through the
existing `applyChangeSet` — so an import is **one typed change set**, the draft token advances
once, and `facility.revision.changed.v1` is the same event every other edit emits. It then
writes `import_features` and one `import_reports` row and emits
`facility.asset-binding.applied.v1`. A mapping names an entity *type*, not an id, so a
pre-existing target is a conflict refused with `409 facility.import.conflict` unless the
caller resolves it; an import never overwrites user-authored geometry. `change-kinds-imports.js`
adds `transform_geometry`, which re-projects through PostGIS or the stored control points and
refuses with `provider_required` rather than guessing.

**T5 — lifecycle and publication.** `publication.js` holds `createRevision` (a branch copies
the graph with fresh ids through a transaction-local id map), `publishRevision` (requires
`VALIDATED`, runs the PUBLISH-phase checks in the same transaction, then sets the revision and
envelope `PUBLISHED` with the checksum, writes the published event and an impact notice, and
freezes the envelope into object storage), `recordApproval`, and `issueImpactNotice`. The
change-set commit now also issues an impact notice for a branched draft.

**T8 — the projection and the browser.** `assistant-surface.js` declares the 19 capabilities,
the 6 UI actions, and the full guide; `createAssistantProjection({ execute })` binds each
handler to the same executor the HTTP routes use. `@ai-infra/assistant` extracts the model's
`uiActions` through the registry, deep-redacts every user-visible string and tool result, and
emits one credential-free audit record per tool call carrying an argument **digest**. The
scope resolver canonicalises the revision and derives `readOnly` from its lifecycle, so a
`VALIDATED` or `PUBLISHED` revision drops every write tool. In the browser, `ui-actions.js`
is the client mirror and dispatcher, `entity-resolver.js` resolves preview and pin through one
path, `workspace-effects.js` is the handle the canvas registers, `Markdown.jsx` matches a
reference by kind **and** id, and `App.jsx` dispatches each settled turn's actions once.

## Decisions worth remembering

* **A package never imports an application, not even in a test.** The first cut of the
  UI-action contract test statically imported `apps/web/src/assistant/ui-actions.js` from a
  facility test, and `import-boundaries.test.js` caught it. The comparison now loads the
  client mirror through a file URL, the same way `packages/rbac`'s client-parity test loads
  the generated permission catalog. The boundary is about what ships in each bundle, and a
  parity test is the one reader that has to cross it — deliberately, not by accident.
* **A capability name is a tool name or a change-kind name, never a third vocabulary.**
  `assistant-integration.md` declared `add_spatial_constraint`, but the registered change kind
  is `assign_constraint`; exposing the former would have broken the shared-name contract for
  one operation. The spec table was corrected and a test now enforces that every capability
  name resolves to a registered tool or change kind.
* **The published capability schema was narrower than the command behind it.** `create_container`
  omitted the design-scope anchor the change kind requires, and `publish_revision` forwarded
  `etag` where the tool's field is `if_match`. Both were found by driving the projection
  through a fake executor rather than by reading it.
* **Independence is disjoint ancestors, not distinct leaves.** Counting databases is not
  counting independent paths; the two checks that reasoned about redundancy disagreed, and the
  one that counted leaves was the wrong one.

## Defects caught

* The UI-action contract test found a real server/client drift on `show_finding`: the server
  required `constraint_id` while the spec's rule is "at least one of `diagnostic_id` or
  `constraint_id`", which is what the client enforced. The server now matches the rule.
* The projection sent `etag` to `publish_revision`, whose tool field is `if_match`; the
  executor's strict argument validation would have refused every publication.
* The PUBLISH-phase run would always emit `facility.revision.writes_immutable`, because that
  check fires for any non-draft revision, so every publication would have persisted a spurious
  blocking ERROR. The publish run presents the envelope as `DRAFT` inside its savepoint and
  writes the real `PUBLISHED` state immediately after; the interim value is never visible.
* The first capacity tie test asserted a tie was refused, but the allocator treated a
  `PROVISIONAL` allocation as terminal, so the second request was never compared with the
  first. The filter now excludes only the terminal states.

## Open

* **`context_token` has no mint route.** The client sends one only when supplied. Making it
  real needs a short-lived revision-bound token issued by the API; the digest and
  `available_actions` fields are the other half of `AssistantComposerContext` that is now sent
  but not yet read by the server.
* **Three canvas layers do not exist.** `set_layer_visibility` for `PHASES`, `DIAGNOSTICS`, and
  `IMPORT_SOURCE`, and `reveal_asset_layer`, validate and then no-op with a stated delta. The
  assistant can ask; the canvas cannot yet answer.
* **The frozen envelope is JSON, not protobuf.** T0 never shipped a protobuf contract, so the
  published object is canonical JSON gzip at the documented key. The interchange contract
  requires the protobuf; the encoding is a delta, not a decision.
* **`pin_policy_reference` still has no store**, and a branch copies waivers whose diagnostics
  it does not copy, so `waiver.scope_mismatch` can fire on a branch until diagnostics are
  re-run. Both are recorded in the plan rather than left for a reader to trip over.
* **The dev seed still carries no capacity rows**, so the capacity surface has no demo data on
  the seeded campuses; the route tests build their own fixture instead.

## Follow-up: three defects the first live call exposed

The first real assistant turn after T8 landed failed, and fixing it uncovered two more. All
three were reproduced against the running stack before being fixed.

1. **A session pointer crossed identities.** `localStorage` remembered which session belonged
   to a context under a key that named only the context, not the acting user. Switching
   identity reloads the page but keeps storage, so the next identity sent the previous one's
   session id and the server refused it — correctly — with `403 ASSISTANT_SESSION_FORBIDDEN`.
   Two fixes: `restore()` now forgets a pointer that resolves to no conversation and no
   session of this caller's, and `submit()` treats that `403` as a stale pointer — forget it,
   clear the id, and retry the same turn once with none.
2. **The model was required to echo a UUID it had never been told.** Every capability schema
   declares `revision_id` required, but the prompt never stated the resolved scope, so the
   model invented one and the executor refused with `403 CONTEXT_MISMATCH`. The prompt now
   states the scope, and — because a live turn showed the model **truncating** the revision id
   even when it was in front of it — the scope identifiers are no longer required of the
   model. The projection binds an omitted `revision_id`/`project_id`/`scenario_id` from the
   resolved context; an explicitly supplied different value is still refused, never rewritten.
3. **Entity links pointed at the wrong object.** `collectEntities` did not know
   `containerId`, so a container's identity was taken from its `phaseId` and the transcript
   emitted `entity://facility.phase/<phase>` for a building. `containerId` and the other
   entity-bearing ids now precede `phaseId` in the identity-field order, and a container links
   to its own entity.

Verified live through the dev proxy against the running API and the configured provider: a
turn now returns `status: ok` with successful `list_containers` and `get_revision_context`
calls, and the entities carry `facility.entity` links with container ids. The fix is covered by
nine new tests across five files; the full workspace suite is green again.
